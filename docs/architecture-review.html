2 · Prioritisation — severity × blast radius

Numbers are finding ids F1…F18. Dashed lines split do-now / do-next / hygiene.

3 · Severity 1 — wrong today, or silently breakable

F1The auto-upgrade job drives the app through its own HTTP routes transport leakno owner

A background job re-enters the application over the network layer: it calls Hono route objects in-process and reads the answers as untyped bodies.

  • server/upgrades/run.ts:30-34 — async function call(route: Hono, path, init) → route.request(path). The only server/upgrades → server/api edge in the whole server.
  • Five route round-trips: GET /files/:id, POST /info/:id, POST /start, GET /plan/:id, POST /organize, POST /link.
  • The only unchecked body casts in the codebase: run.ts:48 (answer.body as FtpListing), :162, :166, :175 (plan.body as DownloadPlan). Everywhere else the codebase casts 0 times.
  • Status code is the error protocol: if (started.status !== 200) return false; — a 404, a 409 "already running" and a 500 all collapse into false. The reason never reaches setState(…, "stopped", note).
  • run.ts:53-61 waitPlanned() polls findDownload() in an unbounded for(;;) … sleep(2000) instead of awaiting the runner that already returns a promise.
  • No test file imports upgrades/run.ts — the 496-line upgrades-episode.test.ts covers pick/stand/place, not the runner.
Effect
The pipeline that decides what enters the library is coupled to its own REST surface. Rename a JSON field, reorder a route, or add a validation guard to /organize and the upgrade job breaks at runtime with no compile error and no failing test.
Blast radius
5 of 8 route files · all of upgrades · the whole download pipeline
Minimal refactor
Lift the two handler bodies of F4 into plain service functions in server/downloads/ and call them directly from run.ts. Delete call(), post(), the Hono import and all 4 casts; the compiler then checks every argument. Keep the routes as 3-line wrappers.
Why not more
Do not introduce a job framework or an event-sourced queue. The loopback is the entire defect; removing it removes the casts, the status-code error protocol and the poll (the service returns the promise waitPlanned is polling for).
Cost
~70 lines moved, 0 behaviour change, 1 file gains coverage it can now have.
F2The quality-band rule has no owner — 4 modules re-derive it with different thresholds no ownerduplicationleak

"Which resolution band is this release in?" is the app's central business decision — it gates upgrades, wish matching and library entry. It is answered independently in four places, and the answers disagree.

  • server/wishlist/target.ts:29-41 — resLabel() and bandOfRes() are the same ladder written twice, six lines apart, differing only in return type (string vs number). One must be derived from the other.
  • server/upgrades/pick.ts:57-61 — a third mapping bandOf(res): MinRes with band >= 2160 / >= 1080, re-wrapping bandOfRes that was imported one line above.
  • server/upgrades/stand.ts:23-27 FORUM_BAND and server/api/wishlist.ts:22 const RES = ["720p","1080p","2160p","none"] — a 5th and 6th copy of the band list, both untyped string[].
  • server/library/name-info.ts:4-24 — its own QUALITY_RE + QUALITY_LABELS that knows 1440p and 480p, two bands MinRes cannot express; server/board/tags.ts:9-16 folds 4k/uhd again; web/windows/library/format.ts exports a 7th ladder QUALITY_RANK/QUALITY_LABEL for the browser.
  • Thresholds disagree: target.ts:39 puts a height of 1920 in the 2160 band and lets width ≥ 3200 promote it; pick.ts:58 compares against a literal 2160; name-info.ts has no band concept at all. Changing one does not change the others.
Effect
A release can simultaneously be "an upgrade" to the picker, "below target" to the wish evaluator, and "2160p" in the library listing. Only upgrades has tests pinning the behaviour (upgrades-place.test.ts: "a uhd encode a little short of 3840 goes in under a 2160 claim"), so drift in the other three is invisible.
Blast radius
wishlist · upgrades · library scan · board sync · catalog API · 2 web windows
Minimal refactor
One module, one ladder: shared/band.ts exporting BANDS, bandOf(height, width), label(band), rank(a,b), parseBand(token). Implement resLabel as label(bandOfRes(…)), delete pick.ts bandOf, and let the forum band / scene-name token maps be *inputs* to parseBand rather than separate ladders. Then move the existing 5 upgrade tests onto it and add the 3 cross-module cases it currently cannot express.
Why not more
Do not unify the *vocabulary* maps (QUALITY_LABELS, tags.ts, FORUM_BAND): those are genuinely different source dialects (scene name, forum id, DB tag). Only the numeric ladder and the comparison need one home.
Cost
~80 lines net, behaviour-preserving if the tests move first. This is the only S1 item that could change behaviour — that is the point.
F3Three background jobs, only two refuse to overlap latent buginconsistent interface
  • server/library/stand.ts:99 startScan() → if (running) return; ✔ (returns void)
  • server/board/sync.ts:449 startSync() → if (state.running) return false; ✔ (returns boolean)
  • server/upgrades/run.ts:245 startUpgradeCheck() → checks only on("upgrades_enabled"). No running guard.
  • server/app/index.ts:64-71 installs setInterval(() => pass.run(), minutes * 60_000) over all four passes and treats them as one shape (Pass.run: () => void), so the return values are already discarded.
  • A check's inner loop is unbounded in time: take() starts a download and waitPlanned() waits for it with no deadline. Any check longer than the interval starts a second one on top.
Effect
Overlapping checks re-run upgradePicks/wishPicks against a library the first check is still mutating → duplicate picks and double downloads of the same thread. The taken set is per-check() call, so it cannot protect across runs.
Blast radius
one file to fix · but it fires on a timer against the ftp + library
Minimal refactor
(a) 3 lines in run.ts: let checking = false, guard at entry, clear in the existing .catch path's finally. (b) give all three jobs the same signature start*(): boolean and let index.ts log the refused start — the shared shape costs nothing and makes the three jobs observable from one place.
Why not more
No scheduler abstraction. A guard per job plus one shared return shape is the whole fix; a "job runner" module would be a shallow wrapper over three lets.
Cost
~10 lines. Highest value-to-risk ratio in the report.
